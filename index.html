About This Explanation

LIMITATIONS

What you are looking at is model-supported feature importance and decision information read directly from the fitted artifacts in this project. It does not establish physical causation.

  • Not SHAP. No Shapley values are computed anywhere in this application. The ablation figures come from re-running the real forest with one feature held at the nominal baseline.
  • No RUL. These are binary classifiers (failure / no failure). There is no remaining-useful-life model, so no life estimate is shown.
  • No failure mode prediction. The models do not predict TWF / HDF / PWF / OSF / RNF. The five failure-mode indicators elsewhere in this app are a documented rule engine, not model output.
  • SVM has no feature weights. An RBF kernel has no per-feature coefficient vector, so no feature importance can be shown for it. Its explanation is limited to the decision score and its most influential support vectors.
  • Relative, not causal. Bar lengths are relative model importance. A high bar means the model relies on that feature, not that the feature causes a failure.
  • Academic prototype. Simulation ranges are visualisation limits, not industrial safety limits.

About the Model

TRANSPARENCY

Random Forest · 300 trees — the only model that runs here. The full serialized forest is bundled in model-data.js; every risk percentage in this app is a real prediction from it, computed in your browser.

Decision Tree and SVM (RBF) were benchmark-only in the original training study. They are now fitted inside this project by train-baselines.mjs on the same AI4I 2020 dataset, with the same features, the same stratified 80/20 split and the same class_weight="balanced" rule — and their artifacts (model-artifacts.js) are loaded at runtime, so all three classifiers score every reading in the browser.

Advisory indicators (TWF/HDF/PWF/OSF/RNF) are rule-based scores using the documented AI4I thresholds. They are labelled as advisory everywhere and must never be read as model probabilities.

Session data (history, settings) is stored only in your browser's local storage. Exports are generated locally from the current session's real values.

This is an academic prototype: not certified for industrial, safety or financial decisions.

What is predictive maintenance & machine failure prediction?
Predictive maintenance detects degradation in machinery before it becomes a breakdown, so interventions can be planned instead of reacting to failures. This project tackles the binary version of the problem: given the current operating readings of a machine, predict whether it will fail (1) or not (0). The AI4I 2020 target column Machine Failure is exactly that label.
Why these three models (Random Forest, Decision Tree, SVM)?
Random Forest (300 trees, class_weight="balanced") is the primary model — an ensemble of decision trees that captures non-linear sensor interactions (e.g. torque × wear) without feature scaling, and it achieved the best documented F1 (0.691) in the training study. Decision Tree is the interpretable single-tree baseline. SVM with an RBF kernel is the margin-based classic for imbalanced tabular data. All three were tuned with stratified 5-fold GridSearchCV optimising F1; only the Random Forest artifact was exported into this project, so only it runs live here.
Why does class imbalance matter (3.39%)?
Only 339 of 10,000 records are failures (~3.39%). A model that always predicts "no failure" would be 96.6% accurate yet completely useless. That is why the project uses a stratified train/test split (failure ratio preserved everywhere), class_weight="balanced" (misclassifying a rare failure costs more), and F1 as the GridSearchCV objective instead of accuracy.
Why F1-score and ROC-AUC?
F1 is the harmonic mean of precision and recall — a single number that punishes both "missing failures" (low recall) and "crying wolf" (low precision), which accuracy cannot do under 3.39% imbalance. ROC-AUC measures how well the model ranks risky machines above healthy ones across all thresholds; the Random Forest's documented test ROC-AUC is 0.969, meaning separation is strong even though the default 0.5 threshold yields a conservative F1 of 0.691.
Why is "Failure Type" excluded from the features?
Failure Type is only populated when a failure has already happened and is derived from the same underlying failure signals — feeding it into a failure predictor is data leakage (the model would cheat by reading the answer). The six legitimate inputs are: Product Type, Air Temperature, Process Temperature, Rotational Speed, Torque, Tool Wear. UDI and Product ID are identifiers, not features. The five failure-mode codes (TWF/HDF/PWF/OSF/RNF) appear in this app only as rule-based advisory indicators, never as classifier outputs.
Simulation vs real telemetry — what is actually real here?
Real: the Random Forest model (serialized trees in model-data.js), every probability/risk percentage it produces, the documented benchmark metrics, and the ablation-based feature contributions. Simulated: the sensor telemetry stream, the machine fleet, the demo script and all scenario values — generated by this prototype, with no physical sensors connected. Every panel that shows simulated data is labelled accordingly.
Where each metric comes from
The Random Forest F1 (0.691) and ROC-AUC (0.969) are the values documented by the original training study. The Decision Tree and SVM metrics shown here were measured by train-baselines.mjs on a stratified 80/20 split (seed 42) of the same dataset, and verify-artifacts.mjs re-scores that held-out split using only the shipped artifacts to prove the two agree. Provenance is labelled on every card, so the two sources are never mixed silently.
Current limitations
Failures are rare and weakly separable: even the best model here leaves most errors as false negatives, so a low risk reading is not a guarantee. The SVM is the weakest of the three (ROC-AUC 0.954 but F1 0.475) and is reported as measured rather than tuned to flatter itself. There is no RUL/time-to-failure model, so no "hours remaining" figure exists anywhere. Advisory indicators are thresholds, not ML. Telemetry is simulated. Results are academic-prototype quality — not certified for industrial or safety decisions.

Viva Mode — Technical Facts

EXAMINATION READY
Which dataset was used?
AI4I 2020 Predictive Maintenance Dataset — 10,000 records, 339 failures (~3.39%), six predictive features (Product Type, Air Temperature, Process Temperature, Rotational Speed, Torque, Tool Wear) plus the binary Machine Failure target. UDI and Product ID are identifiers and are excluded.
What is the target variable?
Binary Machine Failure (0 = no failure, 1 = failure). The application answers "will it fail?", not "which failure mode?" and not "when exactly?".
Why was Failure Type removed from the inputs?
Data leakage. Failure Type is populated only after a failure occurs and encodes the answer. Including it would inflate metrics without real predictive skill. It is shown in the app solely as rule-based advisory indicators.
Why is the dataset imbalanced and what was done about it?
3.39% positives. Remedies: stratified train/test split, stratified 5-fold GridSearchCV, class_weight="balanced" on all three models, and F1 as the optimisation metric instead of accuracy.
Why F1 instead of accuracy?
Accuracy is misleading — predicting "always no failure" gives 96.6% accuracy with zero recall. F1 (harmonic mean of precision and recall) punishes both missed failures and false alarms.
Why Random Forest as the primary model?
Bagging over 300 trees handles non-linear sensor interactions and noisy features without scaling, reduces over-fitting vs a single tree, and it delivered the study's best documented F1 = 0.691 with ROC-AUC = 0.969 under class_weight="balanced".
Why include SVM and a Decision Tree?
They are the classic baselines: the tree for interpretability, the RBF-kernel SVM as a margin-based comparator. Both were tuned in the same study, but only the Random Forest artifact was exported — so in this prototype they are labelled benchmark-only with honest N/A metrics.
What does ROC-AUC = 0.969 mean?
The model ranks a randomly chosen failing machine above a randomly chosen healthy one ~97% of the time. It measures ranking quality across all thresholds — separate from the operating-point F1 of 0.691.
What is predictive maintenance?
Maintaining equipment based on its actual measured condition so failures are prevented or planned for, instead of fixed schedule (preventive) or after breakdown (reactive). This project adds the data-driven prediction layer.
Prediction vs RUL — what does this app output?
A failure probability (0–100%) and a risk band from a binary classifier. It does not predict time-to-failure: no regression model for Remaining Useful Life was trained, so RUL is explicitly displayed as "not available" — no hours-remaining figure is ever shown.
Is this connected to real machines?
No. Telemetry, the machine fleet and all scenario values are simulated by the prototype. The only real ML asset is the serialized Random Forest executing locally in the browser. No sensors, no IoT, no cloud — it is an offline academic prototype.
What are the main limitations?
DT/SVM artifacts not bundled (benchmark-only), advisory indicators are thresholds rather than ML, telemetry is simulated, no RUL model, no probability calibration display for the SVM, and results are not certified for industrial use.
